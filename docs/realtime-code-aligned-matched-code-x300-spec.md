# Real-Time Code-Aligned Matched-Code X300 Transmission Specification

**Status:** Implemented; USRP X300 transmitter acceptance passed

**Date:** 2026-07-13

**Version:** V2

**Scope:** Finite, simulator-aligned GPS L1 C/A matched-code transmission through
the USRP X300 in an authorized conducted path or verified shielded enclosure

**Related:** [researcher/operator guide](realtime-code-aligned-matched-code-x300.md),
[V1 offline matched-code dataset specification](code-aligned-matched-code-dataset-spec.md),
[X300 timing alignment plan](x300-timing-alignment-plan.md), and
[real-time jammer transmission guide](realtime-cw-jammer-x300.md)

## Problem Statement

The researcher can already create an offline dataset in which an independent,
navigation-data-free matched-code source follows selected synthetic GPS L1 C/A
channels in code phase, carrier Doppler, and code-rate Doppler. That workflow is
deterministic and produces clean, jammer, mixed, trajectory, manifest, and
analysis artifacts, but it stops at an IQ file.

The researcher now wants to perform the same experiment as a real-time USRP
X300 transmission. The desired signal for this version is not authentic live
sky. It is the synthetic clean GPS signal generated by the simulator. The
matched-code source must align to that generated clean signal inside the same
process and at the same sample indices, after which both sources must be mixed
digitally and sent through one X300 TX channel.

The existing live tools do not provide that contract. The integrated X300
transmitter owns GPS generation, GPS-time alignment, prebuffering, and UHD
streaming, but it does not render the independent matched-code source from the
clean channels' live state. The jammer-only transmitter renders generic
interference and starts at a relative UHD device time, but deliberately has no
PRN, ephemeris, location, GPS-time, code-phase, or Doppler inputs. Running those
tools as separate processes cannot guarantee a shared sample-zero epoch,
sample-rate authority, channel state, or code-Doppler alignment.

This version must establish the smallest defensible real-time path first. It
must prove that a finite aligned composite can be generated without an offline
IQ handoff and transmitted successfully by the available X300. It must preserve
the offline matched-code threat model and digital J/S definition while adding
strict controlled-RF gates, a hardware-timed start, bounded-memory streaming,
and a complete transmitter manifest.

RF loopback, over-the-air waveform measurement, GNSS-SDR processing, and
victim-receiver behavior are intentionally deferred. Device discovery alone is
also not sufficient evidence of transmission. For this version, success means
that the X300 accepts and completes the exact finite timed burst with no UHD
timing, sequence, or underflow errors and no unexpected digital clipping.

## Solution

Extend `x300tx` with an explicit matched-code composite mode. The existing
clean-only behavior remains the default. No new transmitter executable is
introduced, and the jammer-only transmitter remains jammer-only.

Before transmission, the mode captures or replays the same immutable scenario
inputs used by the offline matched-code workflow, freezes the ordered target
PRN set, selects a calibrated future GPS start epoch, and validates that every
target remains an allocated clean channel for the complete finite run. Network
inputs are closed or made irrelevant before the X300 is armed. Missing,
unstable, unhealthy, geometrically unusable, or unallocatable targets cause a
hard preflight failure; targets are never dropped or changed dynamically.

The X300 is configured before sample generation. The actual sample rate
reported by UHD becomes the sole sample-clock authority for clean generation,
matched-code NCOs, epoch sizes, envelope boundaries, digital measurements, and
the run manifest. The established calibrated GPS-time path binds simulator
sample zero, the first matched-code sample, and the first hardware-timed RF
sample to one recorded GPS week/TOW and one UHD start event.

At each simulator epoch boundary, the clean generator publishes the exact
target-channel code phase, carrier Doppler, code rate, and clean gain that
govern the next samples. A shared stateful matched-code renderer consumes that
state directly in memory. The live path does not read a trajectory file back
during transmission and does not recompute target geometry independently. It
still writes the trajectory as a checksummed provenance artifact so the live
run can later be inspected or replayed offline.

Clean and jammer components remain logically independent until a real-time
digital mixer combines them sample-for-sample in a wide accumulator. One fixed
jammer scale is selected before arming from the frozen scenario and requested
digital J/S. A common composite gain preserves the ratio and provides SC16
headroom. The mixed result is quantized once and streamed through one X300 TX
channel. There is no adaptive J/S controller during the burst.

Matched-code mode is finite and fail-closed. It requires an explicit target
list, J/S, phase seed, clean/jammer timing, device identity, TX gain,
calibration identity, manifest path, and controlled-RF confirmation. A dry run
validates the plan without opening UHD. A live run writes an incomplete
preflight manifest before transmission and replaces it with a complete final
manifest only after the exact planned sample count is sent and all UHD status
messages are drained successfully.

## Implementation Decisions

### Architecture and ownership

- V2 extends the existing `x300tx` executable. There is no new `matchedtx`
  executable.
- Matched-code mode is a combined-scenario mode: `x300tx` generates clean GPS,
  generates the independent matched-code source, mixes both digitally, and
  owns the single UHD stream.
- The composite uses one X300 TX channel. A second TX channel and an external
  RF combiner are not part of the implementation.
- The clean generator remains the alignment authority. RTCM, RINEX, scenario
  metadata, wall-clock data, and UHD time never independently determine jammer
  code phase.
- A reusable stateful matched-code source module is extracted from the offline
  generator. The offline generator becomes a file/manifest adapter around that
  source, while `x300tx` becomes its live in-memory adapter.
- The shared GPS L1 C/A primitive remains the only PRN-code implementation used
  by both desired-signal and matched-code generation.
- The live mixer accepts wide clean and jammer samples and performs one final
  SC16 saturation and quantization. Clean-only mode must remain bit-compatible
  with its pre-V2 behavior when matched-code mode is disabled.
- The existing epoch ring buffer remains the bounded-memory streaming model.
  No complete clean, jammer, or composite IQ file is materialized as a
  prerequisite for live transmission.

### Command and compatibility contract

- Matched-code mode is activated only by an explicit
  `--matched-code-target-prns` list. The list is ordered, duplicate-free, and
  limited to GPS PRNs 1 through 32.
- Live matched-code mode requires explicit values for the target list, digital
  J/S, carrier-phase seed, total finite duration, jammer onset, jammer offset,
  device address, TX channel, TX antenna, TX gain, manifest path, calibration
  identifier, and controlled-RF confirmation.
- The matched-code ramp is explicit or defaults to the V1 global raised-cosine
  value of 10 ms. Its sample-rounded value is recorded.
- The existing finite-duration option defines total samples. Stream-forever and
  continuous operation are rejected whenever matched-code mode is active.
- A new `--dry-run` path performs all checks that do not require an actual UHD
  rate or live send. It does not discover, open, configure, or transmit through
  the X300.
- The J/S option for matched-code mode is distinct from legacy attack J/S
  options. It means total matched-code plateau power relative to total clean
  plateau power at the digital mixer.
- Matched-code mode is mutually exclusive with legacy selective-noise, clone,
  replacement, or other simulator attack configurations. Partial-constellation
  selection is allowed only when it contains every matched-code target and
  passes full-run allocation validation.
- Clean-only `x300tx`, `jammertx`, the bladeRF transmitter, and all existing
  offline source names retain their current command and waveform behavior.
- `jammertx` continues to reject `matched-code`; it does not gain GPS or PRN
  inputs in this version.

### Scenario freezing and target lifecycle

- V2 consumes the immutable scenario inputs established by V1. Live capture,
  if requested, is a preflight stage that produces a frozen scenario before
  hardware arming.
- The frozen scenario defines station position, ephemeris, reference timing,
  requested targets, and all provenance needed by clean generation. Network
  credentials are never written to the run artifacts.
- The future GPS start epoch is selected before the final allocation and power
  preflight so those checks evaluate the exact planned run.
- Every requested target must be healthy, geometrically usable, and allocated
  as a clean simulator channel at every 100 ms epoch boundary for the complete
  finite burst, including clean prefix and recovery.
- The preflight channel-allocation pass is non-mutating with respect to the
  later live renderer. It may use a cloned simulator state, but the live run
  must begin from the same frozen inputs and sample-zero epoch.
- A target that cannot satisfy the full-run requirement causes failure before
  timed TX is armed. There is no intersection policy, fallback PRN, automatic
  replacement, or dynamic target update.
- Once armed, no RTCM or other network update may modify ephemeris, target
  selection, channel allocation policy, or alignment state. A network
  connection may be closed before send; its availability is not a runtime
  requirement.

### Sample-rate and GPS-time contract

- `x300tx` configures the selected X300 channel and reads the actual TX rate
  before initializing clean or matched-code render state.
- The default requested profile remains 2.5 Msps. A live run is rejected if the
  actual rate differs from the requested rate by more than 0.5 Hz. Within that
  tolerance, the actual UHD-reported value, not the requested value, governs
  all sample-to-time and NCO calculations.
- Total duration, onset, offset, and ramp are converted once to exact sample
  indices using the actual rate. Their sample indices are authoritative;
  reported seconds are derived values.
- The finite interval must satisfy zero or more clean-prefix samples, a
  non-empty active plateau after both ramps, and zero or more recovery samples.
  Onset must precede offset, offset must not exceed total samples, and the two
  ramps must not consume the active interval.
- Matched-code live acceptance requires a calibrated GPS-time start. The
  established Trimble time-tag path is the primary mode. An explicit GPS
  week/TOW with a calibrated external or GPSDO time source is also valid when
  the timing provenance is recorded. An uncalibrated wall-clock start is
  development-only and cannot produce an accepted live manifest.
- The first clean sample and first matched-code state both correspond to the
  recorded sample-zero GPS week/TOW. The first UHD packet uses one hardware
  timed-start metadata event for the already mixed stream.
- GPS time at later samples is derived from cumulative emitted sample count,
  the actual TX rate, and the existing GPS-time ppm scale. The same time scale
  governs clean channel state and matched-code updates.
- The existing TX-delay calibration is applied once to the common sample-zero
  epoch. It is not independently applied to the jammer.
- Prebuffering must finish with the required minimum hardware start margin. If
  the chosen future epoch becomes stale, the run aborts or selects a new future
  epoch and repeats preflight; it never silently falls back to an uncalibrated
  immediate start.

### In-memory alignment contract

- Before rendering the first sample of each 100 ms epoch, the clean generator
  publishes one state record per target containing the epoch's first sample
  offset, code phase in chips, carrier Doppler in hertz, code rate in chips per
  second, and clean component gain.
- The in-memory record has the same first-sample and boundary-ownership
  semantics as the V1 target trajectory. A live trajectory artifact records
  those same values at the actual TX rate.
- The matched-code renderer consumes the in-memory record directly. The live
  path never waits for, rereads, reparses, or tails the trajectory artifact.
- At an epoch boundary, the component code NCO is re-anchored to the clean
  channel's boundary code phase, and carrier Doppler and code rate are updated.
  Carrier phase remains independent and continuous across boundaries.
- Code and carrier NCOs advance from sample zero even while the global jammer
  envelope is zero. Consequently, the phase at jammer onset is the
  deterministic result of the complete clean-prefix interval rather than a new
  oscillator reset.
- Every component repeats its target GPS L1 C/A code under a constant positive
  data symbol. It contains no LNAV words, parity, TLM, HOW, ephemeris bits, or
  copied clean navigation data.
- Initial carrier phase is derived deterministically from the explicit run seed
  and target PRN. It is never copied from the clean signal. One seed is used for
  the complete finite run.
- Default component voltage weights are equal. The multi-target composite is
  normalized by actual component power so changing target count does not
  silently change requested total jammer power.
- Renderer output must be invariant to clean epoch ring size, matched renderer
  chunk size, and UHD maximum-send size.
- Offline `matchedgen` output and manifests must remain compatible after the
  shared-source extraction. Given identical trajectory, rate, seed, envelope,
  amplitude, and chunk-independent render length, its matched-only SC16 output
  remains bit-identical.

### Digital mixing and J/S

- Requested J/S is a power ratio in decibels: total navigation-data-free
  matched-code plateau power relative to total synthetic clean plateau power at
  the digital mixer.
- The scale is selected during preflight from the exact frozen scenario. The
  reference measurement window is one second beginning after the jammer rise
  ramp; if the available plateau is shorter than one second, the full plateau
  is used. The manifest records the exact reference sample interval.
- Preflight uses cloned clean and matched renderer state for the reference
  interval so it does not consume or advance live state.
- One jammer scale is fixed before arming and remains constant through the
  burst. V2 does not update amplitude per sample or per epoch to chase clean
  power changes.
- Clean and jammer powers are accumulated separately during the actual active
  plateau. The final manifest reports requested J/S, reference-window J/S,
  achieved full-plateau J/S, and minimum/maximum epoch J/S so drift is visible.
- A single common gain is applied after the requested ratio is established.
  The gain attenuates clean and jammer equally and therefore preserves J/S.
- The common-gain policy uses a conservative full-run component-amplitude bound
  and retains at least 1 dB of predicted SC16 headroom. The selected gain and
  bound are recorded.
- The final composite is saturated and quantized once to interleaved SC16 IQ.
  Any runtime saturation increments a clipping counter, initiates an orderly
  end-of-burst, and makes the run unacceptable.
- Digital J/S, digital amplitude, common gain, and X300 hardware gain are
  distinct quantities. The manifest does not translate them into TX-port power
  or receiver-input J/S.

### UHD streaming and run lifecycle

- A live matched-code run must select exactly one discovered UHD device of type
  X300/X310 at the explicit address. Ambiguous discovery or a different device
  type is a preflight failure.
- Device serial, address, channel count, selected channel, antenna, requested
  and actual rate, GPS L1 center frequency, clock source, time source, and
  requested and actual gain are captured before arming.
- Clean, jammer, and composite samples are produced together into the existing
  prebuffer/ring-buffer lifecycle. Sample production must remain ahead of the
  send cursor.
- The first send carries start-of-burst and one timed-start event. Later sends
  carry neither a new start event nor an independent jammer timestamp.
- Partial UHD sends are retried until the current buffer is complete or a
  fatal event occurs. Rendered, queued, and sent sample counters remain
  separate.
- The planned finite sample count must equal the matched renderer count, clean
  renderer count, composite quantizer count, and UHD sent count.
- The transmitter drains UHD asynchronous status throughout streaming and once
  more after end-of-burst. Underflow, sequence error, and time error counts are
  always recorded.
- Any time error or sequence error is immediately fatal. Any underflow makes
  the run invalid and causes an orderly shutdown at the next safe send
  boundary.
- SIGINT or SIGTERM requests orderly end-of-burst but produces an `interrupted`
  failure status because matched-code mode is finite and exact-count only.
- Exit status is zero only for `dry_run` or a fault-free `complete` finite run.

### Safety and fail-closed activation

- Live matched-code mode is restricted to an authorized conducted path or a
  verified shielded enclosure. The software confirmation is an acknowledgement
  and cannot prove physical containment.
- The tool refuses to open UHD for matched-code transmission unless all
  required live arguments are present, the finite timing is valid, the
  controlled-RF confirmation is set, and a writable manifest can be created.
- Device address, channel, antenna, and gain are explicit in matched-code mode;
  inherited defaults do not satisfy the live safety gate.
- A calibration identifier is mandatory. It identifies the approved timing and
  RF setup but does not claim that the program measured RF power.
- Dry run may omit live confirmation, gain, and hardware discovery because it
  cannot open UHD. Its manifest is labeled `dry_run` and cannot be promoted to
  live evidence.
- No command example in the operator documentation may contain a reusable gain
  or calibration value. Those values must come from the active laboratory
  setup.
- Preflight failures produce no timed TX start. Failures after arming request
  end-of-burst, return nonzero, and preserve a non-complete manifest.

### Artifacts and manifest schema

- Live matched-code mode introduces the versioned manifest schema
  `gps-sdr-sim.x300tx-matched-code.v1`.
- Before UHD transmission, the tool writes a manifest with status `incomplete`
  and all known requested, scenario, safety, and planned timing fields. The
  final manifest is replaced atomically after shutdown.
- Terminal statuses are `dry_run`, `complete`, `interrupted`, `underflow`,
  `sequence_error`, `time_error`, `clipping`, `device_error`, and
  `preflight_error`. A structured failure reason supplements non-complete
  statuses.
- Scenario provenance includes scenario schema and checksum, reference
  position, ephemeris provenance, sample-zero GPS week/TOW, requested targets,
  selected targets, and the full-run target-allocation result.
- Waveform provenance includes the matched-code taxonomy, constant-positive
  data policy, phase seed, per-target initial carrier phases, equal weights,
  normalization, onset/offset/ramp samples, fixed jammer scale, common gain,
  and requested/measured digital J/S.
- The sample contract includes requested and actual rate, SC16 IQ format,
  planned total samples, rendered clean samples, rendered jammer samples,
  quantized composite samples, sent samples, and first/last sample semantics.
- Timing provenance includes the calibrated GPS start mode, GPS week/TOW,
  TX-delay calibration, GPS-time ppm, prebuffer size, UHD timed-start value,
  and whether the start margin was met.
- Hardware provenance includes device type, available serial when reported,
  address, channel, antenna, center frequency, clock/time sources, and
  requested/actual gain and rate.
- Runtime measurements include clean RMS, jammer RMS, composite RMS and peak,
  J/S measurements, common gain, clipping, UHD underflows, sequence errors,
  time errors, interrupted state, and final exit status.
- The live target trajectory uses the established trajectory schema at the
  actual TX rate and is linked by path and SHA-256 checksum. Its path may be
  supplied explicitly or derived beside the required manifest.
- The manifest states that receiver-input power, RF waveform fidelity,
  propagation, RF code alignment, and receiver behavior were not measured by
  this version.

### Build and dependency behavior

- `x300tx` remains an optional UHD build rather than part of the default
  hardware-independent build.
- The X300 target links the shared C/A primitive and the new shared matched-code
  source module in addition to the existing simulator and RTCM support.
- The offline matched-code generator also links the shared matched-code source
  module; it no longer owns a duplicate renderer.
- The default automated test target never invokes a live UHD send. A separate,
  explicitly operator-triggered hardware acceptance target or script owns the
  controlled X300 run.

## Testing Decisions

### Primary behavioral seam

- The highest acceptance seam is one finite matched-code `x300tx` run against a
  provisioned X300 in an authorized conducted path or verified shielded
  enclosure. The operator explicitly supplies the device, RF, timing,
  calibration, scenario, targets, J/S, phase seed, and finite interval.
- Device discovery is a precondition, not the acceptance result. Discovery must
  identify the explicit address as an X300/X310 before the tool is armed.
- The hardware run passes only when all of the following externally visible
  conditions hold:
  - the process exits successfully;
  - the final manifest status is `complete`;
  - planned, clean-rendered, jammer-rendered, composite-quantized, and UHD-sent
    sample counts are identical;
  - UHD time errors, sequence errors, and underflows are all zero;
  - unexpected digital clipping is zero;
  - requested and actual device rate, frequency, channel, antenna, and gain are
    present;
  - the scenario, target trajectory, target set, GPS start, J/S, seed,
    calibration identity, and safety acknowledgement are present and
    checksummed where applicable.
- No spectrum capture, RF loopback, GNSS-SDR result, hardware receiver result,
  `svUsed`, pseudorange residual, or PVT result is required for V2 acceptance.
  The manifest must not imply otherwise.

### Hardware-independent command seam

- A dry-run invocation is the highest automated command seam. It exercises
  command validation, frozen-scenario validation, full-run target allocation,
  trajectory production, exact sample planning, fixed J/S calculation, common
  headroom calculation, safety-field validation appropriate to dry run, and
  `dry_run` manifest generation without opening UHD.
- Dry run uses the requested sample rate as a declared provisional rate. A live
  run repeats all rate-sensitive planning after reading the actual rate.
- Command-level negative tests cover missing targets, duplicate targets,
  missing J/S or seed, continuous mode, invalid onset/offset/ramp, legacy attack
  conflicts, unavailable target allocation, stale start, missing live safety
  fields, unwritable manifest, and unsupported requested rates.

### Shared renderer seam

- A focused C test remains necessary for the signal model that cannot be
  exercised safely in default CI through live hardware.
- Tests assert externally observable samples and metrics rather than private
  helper behavior.
- The shared renderer tests cover authoritative C/A vectors, fractional samples
  per chip, initial code alignment, 100 ms boundary ownership, carrier-Doppler
  updates, code-rate updates, long-run code drift, independent deterministic
  carrier phase, constant-positive data, multiple targets, equal weighting,
  target-count normalization, clean-prefix phase advancement, global ramps,
  chunk-boundary invariance, RMS, and clipping metrics.
- An adapter-parity test feeds the same trajectory and configuration through
  the offline adapter and the live in-memory adapter and requires bit-identical
  matched-only SC16 output before digital mixing.
- A clean-only regression fixture requires `x300tx` sample output to remain
  unchanged when matched-code mode is disabled.

### Prior art

- The existing shared jammer-source test demonstrates the expected pattern for
  known quadrature samples, chunk invariance, deterministic seeds, RMS,
  clipping, and invalid configuration checks.
- The offline matched-code dataset test demonstrates target validation,
  trajectory semantics, multi-PRN normalization, code-domain alignment, and
  manifest augmentation.
- The existing X300 timing work demonstrates actual-rate locking, precise GPS
  time, sample-count-derived time, timed-start metadata, prebuffering, and ppm
  correction.
- The jammer-only live transmitter demonstrates fail-closed controlled-RF
  arguments, preflight/final manifests, exact sent-sample accounting, UHD async
  error handling, and honest separation of digital settings from RF power.
- Existing clean-only and offline test suites must continue to pass. The
  provisioned hardware acceptance is deliberately excluded from the default
  test target.

## Out of Scope

- Alignment to authentic live-sky GPS signals.
- Reconstruction of authentic code phase from RTCM pseudorange.
- Alignment to a victim receiver clock, antenna reference plane, or location
  different from the synthetic scenario reference.
- Dual-X300, dual-channel, multi-device, MIMO, or externally combined clean and
  jammer transmission.
- A jammer-only matched-code RF output.
- Continuous or operator-stopped matched-code transmission.
- Mid-run target addition, removal, replacement, or automatic target selection.
- Live ephemeris or observation updates after the transmitter is armed.
- Copying clean carrier phase.
- Copying or generating LNAV data for the jammer.
- Coherent spoofing, counterfeit navigation messages, false PVT generation, or
  carry-off attacks.
- RF loopback capture or spectrum-analyzer acceptance.
- Quantitative RF code-phase, Doppler, J/S, image, spur, or power measurement.
- GNSS-SDR execution against a live capture.
- Trimble, u-blox, or other hardware-receiver acquisition, tracking, `svUsed`,
  pseudorange-residual, or PVT acceptance.
- Receiver-input power calibration or closed-loop RF J/S control.
- Front-end compression, AGC, multipath, propagation, cable delay, antenna
  delay, or enclosure leakage modeling.
- Open-air transmission or any relaxation of the controlled-RF requirement.
- Multi-seed campaign orchestration or phase-robust research claims. V2 accepts
  one explicit seed per finite run.
- Galileo, GLONASS, BeiDou, QZSS, SBAS, L2, L5, or multi-frequency matched-code
  sources.
- Enabling matched-code in `jammertx`, bladeRF backends, or other transmitters.
- Redesigning legacy simulator attack branches beyond making them mutually
  exclusive with the new mode.
- Changing the V1 offline waveform, dataset schemas, or acceptance results
  except for a behavior-preserving shared-renderer refactor.
- Implementing or evaluating a mitigation algorithm.

## Further Notes

- **Matched-code interference** retains the V1 meaning: navigation-data-free
  GPS L1 C/A components aligned to selected synthetic clean channels in code
  phase, carrier Doppler, and code-rate Doppler, with independent carrier phase.
  It is not ordinary noise and must not be labeled spoofing.
- **Real-time alignment** in this specification is a digital statement before
  the X300 DAC. Clean and jammer share simulator state, actual sample rate,
  sample indices, mixer, and timed burst. RF-path alignment is not yet proven.
- **Digital J/S** is the V1 mixer ratio. Because clean and jammer share one
  linear digital/RF path, it is a useful controlled setting, but it is not a
  measured receiver-input J/S and must be labeled accordingly.
- During planning on 2026-07-13, `uhd_find_devices` using UHD 4.10.0.0
  discovered an X300 at `192.168.5.111`. That is an environment observation,
  not a hardcoded default or proof that a timed transmission succeeds.
- A later version may add a synchronized RF capture and reuse the offline
  correlation and GNSS-SDR gates. That work should extend the evidence boundary
  without changing the V2 digital alignment contract.
- The feature is complete when a researcher can freeze a valid scenario,
  choose target PRNs and a finite clean/active/recovery interval, run the
  fail-closed matched-code mode in `x300tx`, and obtain a `complete` manifest
  proving that the exact planned composite sample count was sent by the X300
  with zero UHD timing, sequence, underflow, or digital-clipping faults.
